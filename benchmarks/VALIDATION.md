# Storage Tracking v1.1 검증 보고

v1.1 구현 시점의 검증 기록입니다. 검증일: 2026-11-14 (Asia/Seoul). Windows 11 10.0.26300, Python 3.13.15, 실제 Tk 8.6 위젯 사용. 저장매체는 확인하지 않아 `unverified`로 기록했습니다. 검증한 구현은 commit `08363a2`로 `main`에 반영되었습니다.

## 변경 내용

- `storage_scanner/options.py`, `config.example.json`, `storage_scanner/gui/app.py`: 기본 `gui_update_ms`를 1,000ms로 변경했습니다. 사용자 지정 700ms 등 기존 값은 유지합니다. 기본 검색 크기는 100MiB이며 더 작은 값도 허용합니다.
- `storage_scanner/core/results.py`: 크기만 달라진 상위 폴더도 변경 집합에 기록합니다. 불변 노드 조회와 개수/페이지의 일관된 스냅샷 읽기를 추가했습니다. GUI는 최대 32개 항목의 페이지를 짧은 락 안에서 복사한 뒤 락 밖에서 Tk를 갱신합니다. 배치 저장은 기존처럼 64개씩 락을 해제합니다.
- `storage_scanner/gui/app.py`: 검색 시작 시 현재 실행의 저장소를 연결합니다. 기존 상태 타이머가 검색 중 변경 확인도 예약합니다. collector가 마지막 배치까지 처리해 `finished`를 게시하면 남은 변경을 반영하며, 완료/취소 시 트리를 재구축하지 않습니다.
- `storage_scanner/gui/tree_view.py`: 변경 집합을 최대 32개씩 GUI 대기 큐로 옮겨, 화면에 있는 행의 합계와 열린 폴더의 새 결과만 처리합니다. 페이지 오프셋·선택·확장 상태를 유지합니다. 접힌 폴더는 펼칠 때 현재 페이지를 읽습니다. 한 번에 최대 150개 작업/약 12ms를 처리하고 남은 작업은 `after(1)`로 이어갑니다.
- 트리 초기화는 새 Treeview로 교체한 뒤, 이전 위젯의 실제 렌더 항목만 삽입 역순으로 나눠 삭제합니다. 부모보다 자식이 먼저 삭제되므로 큰 하위 트리를 한 번에 지우지 않습니다. 빈 위젯만 마지막에 destroy합니다. 렌더 세대와 실행별 저장소/ID, 이전 위젯 이벤트 검사를 통해 오래된 작업을 격리합니다.
- `tests/test_gui.py`, `tests/test_results.py`, `tests/test_options.py`: 실제 Tk 회귀 테스트와 설정/변경 추적 테스트를 추가했습니다. `README.md`와 벤치마크 도구도 현재 동작에 맞췄습니다.

엔진·플랫폼 계층·controller의 순회 및 수집 로직은 변경하지 않았습니다. 메타데이터만 조회하며, 조건에 일치한 파일만 RAM에 저장하고 합산합니다. 엔진 배치는 512개/0.25초, 진행 알림은 0.2초를 유지합니다.

변경 전 48개 테스트 중 47개 통과, 1개 건너뜀. 변경 후 54개 중 53개 통과, 1개 건너뜀. 건너뛴 테스트는 Windows 권한 때문에 실제 심볼릭 링크를 생성할 수 없는 경우입니다. 실제 junction 회귀 테스트는 통과했습니다. 컴파일과 공백 검사도 통과했습니다.

실제 Tk 테스트에서 다음을 확인했습니다.

- 기본 1초 타이머를 쓰는 검색이 아직 실행 중일 때 파일과 상위 폴더가 표시되고, 다음 배치에서 기존 폴더 합계가 100 → 300바이트로 갱신됩니다.
- 접힌 하위 폴더는 placeholder만 유지하며, 펼치면 그 시점의 두 파일이 표시됩니다. 취소의 마지막 부분 배치까지 세 파일/700바이트를 반영하고 저장 수와 최종 요약 수가 일치합니다.
- 라이브 페이지를 200 → 250 → 400개까지 추가 로딩해도 첫 페이지 항목 ID·선택·확장 상태가 유지되고 중복 삽입이 없습니다.
- 1,800개 폴더의 변경이 한 프레임 예산을 초과해도 heartbeat가 실행되며, 남은 변경을 모두 반영합니다. 접힌 자식 전체를 렌더하지 않습니다.
- 20,000개 실제 Tk 자식 항목을 갖는 단일 하위 트리를 초기화하고 연속 재시작해도 매 삭제가 leaf에만 적용됩니다. 이전 렌더 콜백/위젯 이벤트는 새 트리를 변경하지 않고, 모든 이전 위젯이 정리됩니다. Tk 콜백 오류는 없었습니다.
- 20,000개 결과 스트리밍 중 취소/재시작, 정상 완료 직후 행 유지, 늦은 수집 결과 격리, 최종 수집 완료 순서, 완료 알림 중복 방지, 폴더 컨텍스트 메뉴도 통과했습니다.

비교 도구는 기본 기준 commit `2b67874e30c32eb669c1ce3c8cbb0e42310d03c6`의 추적 파일을 소유한 임시 폴더에 풀어 실행합니다. `main` 반영 후에도 같은 기준으로 재현할 수 있으며 `--baseline-ref`로 다른 기준을 지정할 수 있습니다. 기준과 변경 버전은 같은 로컬 볼륨의 새 임시 fixture를 사용하며 각 측정 프로세스를 분리합니다. 합성 인덱싱/트리 fixture는 메타데이터와 Tk 항목만 만들고 디스크를 스캔하지 않습니다. 당시 원시 결과는 [results/v1.1/](results/v1.1/)에 보관하고 새 실행 결과는 Git 추적에서 제외합니다. 도구별 사용법은 [README.md](README.md)를 참고하세요.

캐시는 비우지 않았고 외부 부하를 통제하지 않았습니다. 짧은 측정의 차이를 속도 개선/악화 배수로 일반화하지 않습니다. 엔진+저장 시간은 저장만의 시간이 아니며, 합성 인덱싱 도구가 별도로 저장 시간을 측정합니다. GUI 전체 시간에는 시작부터 상태 타이머 대기가 포함되며, 기본값 변경으로 짧은 검색의 완료 표시 대기가 늘 수 있습니다.

## 제외 사항과 남은 제한

사용자 요청에 따라 크기순 정렬은 구현 범위에서 제외했습니다. 현재 append-only 자식 인덱스의 파일시스템 탐색 순서를 유지합니다.

이전 위젯은 정리 완료까지 잠시 메모리에 남습니다. 빠른 연속 재시작은 동시에 정리할 위젯 수를 늘릴 수 있습니다. 표시된 결과만 정리하고 저장소 전체를 Tk에 불러오지는 않습니다. 작업 예산은 하드 실시간 보장이 아니며 OS/Tk의 개별 호출과 스레드 경쟁에 따른 지연이 남습니다. 최종 전체 창 종료 시의 동기적 Tk 위젯 해제는 이번 재시작 최적화 범위에 포함하지 않았습니다.

실제 Linux GUI/마운트 및 네트워크·이동식 장치, SSD/HDD별 대형 스토리지 성능은 이번에 검증하지 않았습니다. 사용자 디스크 전체를 스캔하지 않았으며, 테스트에서 소유한 임시 폴더만 스캔했습니다.
