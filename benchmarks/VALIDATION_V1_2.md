- 기준/최신 원격 `main`: `35cdbfc60f0979a7361aef44f901aebe0599f719`. 작업 시작 시 fetch로 동일함을 확인했다.
- 작업 브랜치: `feat/folder-scanner-v1.2`. 병합 전 PR 리뷰 대상으로 구현했다.
- 환경: Windows 11 `10.0.26300`, Python 3.13.15, Tk/Tcl 8.6.15. 저장 매체 종류와 OS 캐시는 통제하지 않았다.

파일의 기존 공개 API는 이동하지 않았다. 새 폴더 모듈은 파일 스캐너의 모델·저장소·알고리즘·컨트롤러를 import하지 않는다. AST 아키텍처 테스트가 양방향 의존을 검사한다. 두 컨트롤러는 앱이 전달하는 잠금 하나를 사용해 실제 worker 순회를 직렬화한다. GUI에서 스레드를 join하지 않는다. 늦은 알림은 실행 ID와 저장소 객체 동일성을 함께 검사하며, 트리는 기존 세대 격리와 숨긴 위젯의 분할 삭제를 유지한다.

## 폴더 합산과 표시

엔진은 해당 디렉터리에서 읽은 파일의 직접 용량만 `DirectoryDelta(path, direct_bytes)`로 전달한다. 기본 128개 엔트리마다 용량 증분을 만들고 시간·배치 한도에 맞춰 전달한다. 저장소는 직접 용량을 별도 보관하고 증분을 조상마다 한 번씩 반영한다. 자식의 최종 누적 합계를 다시 더하지 않는다. 취소 시 남은 증분도 전달한다. 일반 파일이 stat 시점에 디렉터리로 바뀐 경우는 오류로 집계한다.

개별 파일 경로나 파일 결과 객체를 저장하지 않는다. 0B 하위 폴더는 생략하고 선택 루트는 항상 표시한다. 저장소는 `scanning`, `complete`, `partial` 상태를 구분한다. 취소·오류 시 `partial`이며 파일 루트는 폴더 모드에서 오류로 집계한다. 파일 루트와 파일 bind 마운트의 기존 파일 모드 지원은 유지한다.

집계 중에는 발견 순서를 유지한다. 수집 스레드가 종료 시 부모별 자식 인덱스를 용량 내림차순으로 정렬한다. 정렬은 잠금 밖에서 수행하고 부모별로 짧게 교체한다. UI는 이미 로드한 범위만 예산 내에서 다시 조회·이동하므로 선택/확장과 Tk 항목 ID를 유지한다. 아직 로드하지 않은 전체 결과를 미리 삽입하지 않는다. 선택된 기존 항목을 없애지 않기 위해 최종 상위 페이지와 기존 페이지의 합집합을 유지한다. 따라서 이전에 불러온 상위 페이지 밖 항목은 뒤에 남을 수 있다. 파일 모드에는 정렬을 추가하지 않았다.

## 자동 테스트와 실제 Tk

작업 전 `unittest discover`: **58개 중 57개 통과, 1개 건너뜀**. 지시서에 인용된 과거 54개보다 현재 기준 코드의 테스트 수가 많았다.

최종 `python -m unittest discover -s tests -v`: **80개 중 79개 통과, 1개 건너뜀**. `python -m compileall -q storage_scanner tests benchmarks` 통과.

- 모든 파일 크기 합산과 100MiB 파일 모드의 차이, 루트 직접 용량·다단계 조상 합계·중복 방지, 0B·빈 폴더·제외 경로.
- 한글/공백/특수문자, 깊은 반복형 순회, 수천 형제 폴더, 파일 수가 많아도 폴더만 저장함을 검증.
- 마운트 경계, 중복/중첩 루트, 파일 단위 경계, Windows 실제 junction 순환 회피, 접근 거부·삭제 경쟁·파일/폴더 타입 변경.
- 취소 후 마지막 증분 반영, 미완료 상태, 같은 모드 재시작의 늦은 배치 격리, 수집 실패/worker 실패 시 종료·잠금 해제.
- 실제 worker 경로에서 File→Folder, Folder→File, File→File, Folder→Folder 순회 중첩 방지.
- 실제 Tk에서 모드 선택의 자동 실행 방지, 파일 전용 최소 크기, 이전 알림의 실행 ID 충돌 방지, 1,000ms 부분 갱신, 취소 최종 합계.
- 실제 Tk에서 200개 페이지, 완료 후 큰 폴더 우선 표시, 선택/확장 유지, 4,000개 렌더 항목이 있는 상태에서 반복 전환과 지연 정리, 오래된 렌더 콜백 격리.

유일한 건너뜀은 기존 파일 스캐너의 실제 symlink 생성 테스트다. Windows symlink 권한이 없어 생략했다. 실제 junction 테스트는 양쪽 모드 모두 통과했다. Linux 실기기 검증은 수행하지 않았다. 기존 Linux 경로/마운트/bind 정책 단위 테스트는 통과했다.

기준 archive와 현재 코드를 새 프로세스에서 순차 실행하는 기존 `compare_versions`를 사용했다. 아래는 3,000개 엔트리, 3회 중앙값이다. GUI는 1초 타이머 대기를 포함하며 root만 펼친다.

| 일치 파일 3,000개 | 20.15→23.64 | 45.60→48.91 | 67.21→69.24 | 36.83 / 10.42 | 53.20 | 46.74→47.17 |

세부 값과 실제 렌더 시간은 [file-comparison.json](results/v1.2/file-comparison.json)을 기준으로 한다. 엔진·저장 포함 프로세스 peak RAM은 약 25~26MiB이며 새 GUI는 두 모드 위젯/모듈을 준비하는 비용이 포함된다.

GUI 전체 중앙값은 빈 폴더 0.9053→0.9056초, 일치 없음 0.9026→0.9033초, 모두 일치 0.9326→0.9318초였다. 모두 일치 시 실제 삽입 노드는 양쪽 모두 201개다.

짧은 작업의 변동을 확인하기 위해 같은 fixture를 재생성하지 않고 baseline/current를 번갈아 먼저 실행하는 7회 비교도 수행했다. 파일 케이스는 10,000개, 빈 폴더는 3,000개다.

| 시나리오 | 엔진 기준→현재 ms | 저장 포함 기준→현재 ms |
| --- | ---: | ---: |
| 빈 폴더 | 247.29→251.54 | 259.79→262.19 |

일치 파일 엔진 중앙값은 거의 같았다. 저장 포함 중앙값은 약 12% 높았으며 원시 표본 범위는 기준 116.90~224.56ms, 현재 118.97~258.30ms로 크게 겹쳤다. `core/scanner.py`, `core/results.py`, `gui/tree_view.py`는 기준과 diff가 없고 이동한 PathFilter의 메서드 구현도 동일하다. 캐시·OS/외부 부하·GC 영향을 분리하지 못했으므로 성능 회귀가 없다고 단정하거나 특정 원인으로 확정하지 않는다. [shared-fixture.json](results/v1.2/shared-fixture.json)에 모든 표본을 보관한다. 제어된 환경에서 추가 반복 비교를 권장한다.

## 폴더 모드 성능

`python -m benchmarks.folder_scenarios --files 20000 --repeat 3`으로 엔진 단독, 저장 포함, GUI 및 별도 Python 할당량 추적을 각각 새 프로세스에서 측정했다. 최종 수치는 [folder.json](results/v1.2/folder.json)에 보관한다. 아래 표는 해당 JSON에서 생성한다.

| Scenario (files / folders) | Engine ms | With store ms | Index / sort ms | GUI scan / wall ms | GUI collect / render ms | Heartbeat gap ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| few_folders_small (5,000 / 5) | 18.18 | 19.42 | 0.91 / 0.02 | 29.18 / 897.73 | 1.42 / 0.63 | 24.63 |
| few_folders (20,000 / 5) | 82.95 | 85.51 | 2.14 / 0.02 | 99.23 / 913.43 | 2.72 / 0.85 | 25.77 |
| many_folders (20,000 / 4,001) | 454.07 | 518.93 | 84.50 / 3.45 | 689.66 / 1015.22 | 105.96 / 10.91 | 35.67 |

| Scenario | Stored folders | Engine / store / GUI peak MiB | Python peak bytes (separate traced run) |
| --- | ---: | ---: | ---: |
| few_folders_small | 5 | 25.34 / 25.29 / 46.66 | 499,091 |
| few_folders | 5 | 25.21 / 25.32 / 46.71 | 499,131 |
| many_folders | 4,001 | 25.82 / 27.81 / 49.31 | 2,825,410 |

GUI 전체 시간에는 시작/발견 폴링, 1초 갱신 대기, 수집 및 렌더가 포함된다. 저장 포함 시간과 엔진 단독 시간은 서로 다른 프로세스의 측정이므로 단순 차이를 순수 저장 비용으로 해석하지 않는다. `index_seconds`는 저장 callback의 실제 누적 시간이고 GUI의 `collector_store_seconds`는 수집 스레드의 add_batch 누적 시간이다. 폴더 정렬 시간은 별도 `finalize_seconds`로 측정한다. 메모리 추적 실행의 시간은 일반 실행과 비교하지 않는다.

파일 수 5,000→20,000에 대해 같은 폴더 수에서 인덱스 노드 수와 Python 최대 할당량이 거의 일정했고, 파일 수가 같아도 폴더 수가 4,001개가 되면 할당량이 증가했다. 이는 개별 파일 경로를 보관하지 않는 설계와 일치한다. 프로세스 peak RAM에는 인터프리터·Tk·볼륨 탐색 등이 포함되므로 저장소만의 메모리나 하드 상한을 뜻하지 않는다. 최대 heartbeat 간격은 UI 지연 관측치이며 모든 환경에서의 응답 시간 보장이 아니다.

## 제한과 후속 검증

- 논리적 `st_size` 합산이다. 희소·압축 파일의 물리 점유량과 다르고 하드링크는 경로별로 센다. 파일 내용/해시를 읽지 않는다.
- 오류나 취소 결과는 부분 합계이며, 검색 중 파일/마운트 변경에 대한 원자적 스냅샷을 제공하지 않는다. OS 호출 자체는 강제 중단하지 않는다.
- 두 모드는 독립 실행이며 결과·캐시를 공유하지 않는다. 모드 전환 후 Scan / Restart를 눌러야 한다. 폴더 모드에서 최소 크기는 적용되지 않는다.
- Linux 실기기와 실제 symlink 생성 권한이 있는 Windows에서 추가 통합 검증이 필요하다.
- 짧은 파일 성능 시험의 변동과 저장 포함 중앙값 차이는 리뷰 시 확인할 항목이다. 드라이브 전체 검색이나 범위 밖 기능을 추가하지 않고 제어된 fixture로 재검증한다.
